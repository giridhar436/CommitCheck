Lesson 0001

From JavaScript to TypeScript: The Architecture Contract

Grounding your first step into full-stack development through typed domain boundaries.

Mission Connection: When you build an AI SaaS application from scratch, data flows constantly between external APIs (like Google Meet and Linear), relational databases, and UI components. In plain JavaScript, a single misspelling can quietly break an entire feature in production. TypeScript guarantees that your data contracts match everywhere before your app ever runs.

1. The Problem with Plain JavaScript at SaaS Scale

In standard JavaScript, objects are flexible dictionaries. You can create an object with any keys you want:

// Plain JavaScript
const project = {
  title: "Client Redesign",
  clientEmail: "sarah@client.com",
  repoUrl: "https://github.com/agency/redesign"
};

// Later in your code, an easy typo happens:
console.log(project.client_email); // undefined! No warning, silent bug.

In a large application with authentication, databases, and AI webhooks, silent undefined errors are the number one cause of production downtime.

2. How TypeScript Solves This: The Interface Contract

TypeScript adds a static type layer on top of JavaScript. You define an interface—a strict blueprint of what an object MUST contain:

// TypeScript definition
interface Project {
  title: string;
  clientEmail: string;
  repoUrl: string;
}

const project: Project = {
  title: "Client Redesign",
  clientEmail: "sarah@client.com",
  repoUrl: "https://github.com/agency/redesign"
};

// Now if you type:
// project.client_email
// The TypeScript compiler immediately throws an error:
// Property 'client_email' does not exist on type 'Project'. Did you mean 'clientEmail'?

The Key Mental Model

TypeScript does not change how JavaScript behaves when your code executes in the browser or on the server. Instead, TypeScript acts as a compile-time safety net inside your editor. When Next.js builds your app, all TypeScript types are completely erased, leaving behind clean, standard JavaScript.

3. Seeing TypeScript in CommitCheck

In this repository, look at how roles and tasks are represented. Instead of passing loose strings like "freelancer" or "client", we define explicit union types:

// Defined in the domain architecture
type UserRole = "FREELANCER" | "CLIENT";

interface AuthenticatedUser {
  id: string;
  email: string;
  role: UserRole;
}

If someone accidentally tries to assign role: "ADMIN" or role: "developer", TypeScript stops the build immediately. This prevents security loopholes across our OAuth boundaries.

Concept Check 1: Why does CommitCheck use a TypeScript interface for task data instead of a plain JavaScript object?
It runs faster inside the browser engine.
It catches invalid property names before execution.
It automatically saves records to the database.
It encrypts sensitive information inside the cloud.
Concept Check 2: What happens to TypeScript type annotations when Next.js builds the production application?
They remain embedded inside production bundles.
They are sent to the database.
They are completely stripped from JavaScript.
They execute security checks during runtime.
